# Remaining lmweblab scenarios

Scenarios 07, 08, 09, 10 and 12 are developed against synthetic transports. No real AWS calls were made for this work. Live testing requires the Lead go after scenarios 03–06; source scripts explicitly reject live mode meanwhile.

New typed APIs are `Cloud.sqs_event_source_mapping(queueUrl, functionArn, batchSize[, runId])`, `sqs_event_source_mapping_get(arn, runId)`, `sqs_event_source_mappings(runId)`, `sqs_redrive(source, dlq[, runId])`, `sqs_redrive_clear(source[, runId])`, `dynamodb_item_conditional(table, key, value, condition[, runId])`, and `s3_presigned_put(bucket, key, bytes, contentType, expirySeconds[, runId])`. `QueueWorker.status/delete` support durable resume, actual ownership tags and bounded deletion. Inventory is scoped to the run's `lmaws_<run>_worker` function. Batch size is 1..10; redrive uses maxReceiveCount 3. The conditional-write API allows only `attribute_exists(pk)` and `attribute_not_exists(pk)`. Presigning supports PNG/JPEG/WebP/GIF, 1..10 MiB, 1..900 seconds, exact signed Content-Length and Content-Type. It does not inspect image bytes. The gallery scenario applies a stricter 1 MiB cap.

`Serverless.step("queues", ...)` and `step("worker", ...)` add durable queue/worker receipts with mapping-first teardown. Custom Lambda log groups follow `lmaws_<slug>_logs_<run>`, including `lmaws_s07_worker_logs_<run>`; no default `/aws/lambda/` groups are requested. A session-login password comes only from the private `LMWEBLAB_DEMO_PASSWORD` environment; unset or empty passwords fail closed. These are bounded demonstrations, not production authentication.

`Web.step("cache", "{\"default_ttl\":30,\"max_ttl\":60}")` accepts static default TTL 0..300, max TTL between default and 3600. API origins cannot acquire a positive default TTL. Existing mixed CloudFront distributions retain two origins and uncached `/api/*`. Versions/aliases are unnecessary for these five patterns; scenario 12 uses the existing nano/static DNS cutover.

Common Lambda actions: `lambda:CreateFunction`, `GetFunction`, `GetFunctionConfiguration`, `CreateFunctionUrlConfig`, `GetFunctionUrlConfig`, `AddPermission`, `InvokeFunction`, `InvokeFunctionUrl`, `DeleteFunctionUrlConfig`, `DeleteFunction`, `ListFunctions`; `iam:PassRole` with `iam:PassedToService=lambda.amazonaws.com`; `sts:GetCallerIdentity`; `logs:CreateLogGroup`, `ListTagsLogGroup`, `ListTagsForResource`, `PutRetentionPolicy`, `DeleteLogGroup`, `DescribeLogGroups`. The execution role additionally uses `logs:CreateLogStream` and `PutLogEvents` in the custom groups. The exact branches of AWS SDK tagging APIs depend on service, and no broad admin fallback is permitted.

AWS documents `lambda:CreateEventSourceMapping` with no resource type, requiring Resource `*`. Its supported keys are `lambda:FunctionArn`, `aws:RequestTag/${TagKey}`, and `aws:TagKeys`. A proposed statement is:

```json
{"Effect":"Allow","Action":"lambda:CreateEventSourceMapping","Resource":"*","Condition":{"ArnLike":{"lambda:FunctionArn":"arn:aws:lambda:us-east-1:${aws:PrincipalAccount}:function:lmaws_*"},"StringLike":{"aws:RequestTag/lmaws_test":"?*"},"ForAllValues:StringEquals":{"aws:TagKeys":["lmaws_test"]}}}
```

`lambda:GetEventSourceMapping` and `DeleteEventSourceMapping` use resource `arn:aws:lambda:us-east-1:${aws:PrincipalAccount}:event-source-mapping:*`, with `lambda:FunctionArn` and `aws:ResourceTag/lmaws_test` restrictions. `lambda:TagResource` is also required on mapping resources when creating with tags, constrained by request tag/tag keys. `lambda:ListTags` needs mapping-resource permission. `lambda:ListEventSourceMappings` is a Resource `*` read; the host supplies FunctionName for the exact run worker. No UpdateEventSourceMapping permission is needed by this implementation. UUID mapping ARNs cannot be restricted by a `lmaws_` name, so tags and target-function conditions matter. The Lead must review the matching permissions boundary and policy lint before any grant; these additions were not applied.
