# Remaining lmweblab scenarios

The Lead authorized 07 separately under lmaws_session v7b. Its functional tests passed, cleanup recovered from a missing-object Get denial, and both attempts ended empty. 08/09/10/12 have their earlier live evidence. See [lmweblab RESULTS](https://github.com/lmctl-ai/lmweblab/blob/main/scenarios/RESULTS.md). All tests use profile lmaws, us-east-1 and fresh run IDs; role/IAM/profile files are untouched. Scenario 07 additionally requires LMWEBLAB_WORKER_LIVE_GO=1 alongside the general go flag. The current source build is required.

New typed APIs are `Cloud.sqs_event_source_mapping(queueUrl, functionArn, batchSize[, runId])`, `sqs_event_source_mapping_get(arn, runId)`, `sqs_event_source_mappings(runId)`, `sqs_redrive(source, dlq[, runId])`, `sqs_redrive_clear(source[, runId])`, `dynamodb_item_conditional(table, key, value, condition[, runId])`, and `s3_presigned_put(bucket, key, bytes, contentType, expirySeconds[, runId])`. `QueueWorker.status/delete` support durable resume, actual ownership tags and bounded deletion. Inventory is scoped to the run's `lmaws_<run>_worker` function. Batch size is 1..10; redrive uses maxReceiveCount 3. The conditional-write API allows only `attribute_exists(pk)` and `attribute_not_exists(pk)`. Presigning supports PNG/JPEG/WebP/GIF, 1..10 MiB, 1..900 seconds, exact signed Content-Length and Content-Type. It does not inspect image bytes. The gallery scenario applies a stricter 1 MiB cap.

`Serverless.step("queues", ...)` and `step("worker", ...)` add durable queue/worker receipts with mapping-first teardown. Custom Lambda log groups follow `lmaws_<slug>_logs_<run>`, including `lmaws_s07_worker_logs_<run>`; no default `/aws/lambda/` groups are requested. A session-login password comes only from the private `LMWEBLAB_DEMO_PASSWORD` environment; unset or empty passwords fail closed. These are bounded demonstrations, not production authentication.

`Web.step("cache", "{\"default_ttl\":30,\"max_ttl\":60}")` accepts static default TTL 0..300, max TTL between default and 3600. API origins require both default and maximum TTL zero. Existing mixed CloudFront distributions retain two origins and uncached `/api/*`. Versions/aliases are unnecessary for these five patterns; scenario 12 uses the existing nano/static DNS cutover.

## IAM scope and missing-object reads

The Lead reports v7b applied. This document describes that grant and the checked-in builder; these tests do not query active IAM. EsmCreate scopes the function ARN and request tags. EsmTag permits the single lmaws_test request key. The host supplies it only inside creation; it forbids standalone mapping tagging. EsmOwn scopes mapping ARNs and requires a nonempty lmaws_test resource tag. Reads includes lambda:List*, covering mapping lists. Existing mappings are never tagged by the host.

The execution role additionally uses `logs:CreateLogStream` and `PutLogEvents` in the custom groups. The exact branches of AWS SDK tagging APIs depend on service, and no broad admin fallback is permitted.

The observed denied operation was `lambda:GetEventSourceMapping` on resource `*` after an accepted deletion. The v7b `EsmOwn` resource pattern is `arn:aws:lambda:us-east-1:*:event-source-mapping:*`, with `StringLike` on `aws:ResourceTag/lmaws_test` matching `?*`. A permitted mapping list proved the resource absent. Functional testing stopped at the denial; no grant was changed.

The deletion client now validates region/account, looks up the exact mapping ARN through a bounded account-wide list, checks the actual tags/queue/function before deleting a present mapping, and polls list-based absence after deletion. It never treats arbitrary AccessDenied as absence. Inventory for a run's exact worker includes foreign/untagged mappings as owned=false rather than hiding them. Mapping tags are only supplied atomically inside CreateEventSourceMapping. No UpdateEventSourceMapping permission is used.

Sources: [Lambda service authorization](https://docs.aws.amazon.com/service-authorization/latest/reference/list_lambda.html), [SQS event source configuration](https://docs.aws.amazon.com/lambda/latest/dg/services-sqs-configure.html), [S3 PutObject headers](https://docs.aws.amazon.com/AmazonS3/latest/API/API_PutObject.html).

Queue-worker accounting reserves up to 300 worker deliveries for 100 admitted API messages, full configured runtime/memory, log bounds and SQS request bounds. These are short-run price estimates, not an enforced AWS billing ceiling against arbitrary traffic. The upload driver divides its cap between the paired Serverless and Web journals and sums their final estimates.

Worker log reconciliation runs only after both functions and the mapping have been removed. It reuses the bounded final-delivery drain and exact creation/name/time/tag receipt checks, and can be repeated after teardown.
